# MEDEXA — история, статистика и персональный прогресс (этап 5)

Основа: `3e04c071b1a7f0c3b8c80827b2d2ead8b70edfb0`.
Schema head: `0010_progress_statistics`. API v1, существующая cookie-сессия,
permission `progress.self` для собственных данных. Администратор не получает
доступа к чужой статистике через эти маршруты. Frontend не интегрируется этим PR.

## Источники и отсутствие двойного учёта

Единственный источник результатов — `attempts.status='completed'` текущего
`user.progress_epoch`, их sealed items и immutable responses. Exam timeout уже
представлен как completed/finish_reason=timeout и входит в показатели. Active и
abandoned, включая проверенные Learning-ответы до выхода, не входят.

Нет второй истории ответов, копии результатов, накопительных счётчиков, обработчика
начислений или асинхронного обновления аналитики. PostgreSQL вычисляет read models
из первичных записей. Финализатор по-прежнему атомарно сохраняет один результат;
повтор finish, idempotency replay, worker restart и повторное чтение не могут
прибавить ещё одно событие. Сводки видят либо завершённую транзакцию целиком, либо
предыдущее состояние. Исторические результаты и миграции 0001–0009 не переписаны.

Сохранены прежние Learning/Exam действия, deadline/finalizer, CAS и безопасные DTO.
Home может финализировать просроченный Exam тем же существующим финализатором,
прежде чем вернуть согласованную сводку/историю. Это не новое начисление статистики.

## API

Все пути ниже начинаются с `/api/v1`. Ответ: Envelope `{data,meta}`;
пагинируемые списки `{data,page:{next_cursor,has_more},meta}`.

| Метод / путь | Параметры и назначение |
|---|---|
| GET `/me/attempts` | mode=learning/exam, discipline_id, topic_id, start/end (даты), limit=1..100, cursor; завершённая история текущего epoch |
| GET `/attempts/{id}` | Существующий owner-only resume/terminal объект с mode/scope/IDs и immutable result |
| GET `/attempts/{id}/result` | Существующий агрегат завершённого Learning/Exam |
| GET `/attempts/{id}/result-review` | selection=incorrect (по умолчанию, ошибки+пропуски), skipped или all; limit=1..100, cursor |
| GET `/me/statistics` | period=all/week/month; компактная общая сводка |
| GET `/me/progress` | Общая сводка и unattributed_topic_responses для старой неоднозначной истории |
| GET `/me/progress/disciplines` | Прогресс по дисциплинам; limit/cursor |
| GET `/me/progress/topics` | Прогресс по темам; discipline_id?, limit/cursor |
| GET `/me/topics/{id}/summary` | completed_count, best_percent, ever_wrong/unresolved_wrong; nullable favorites/not_configured |
| GET `/me/mistakes` | group_by=topic/discipline; те же реальные групповые показатели ошибок, limit/cursor |
| GET `/me/activity` | week_start? — локальный понедельник, 7 календарных дней |
| GET `/me/calendar` | start/end, от 1 до 366 календарных дней включительно |
| GET `/me/result-trends` | Те же start/end; дневной средний результат и фактические числа завершений/ответов |
| GET `/me/recommendations` | limit=1..10; доступные слабые темы на основании истории |
| GET `/me/daily-topic` | Один фиксированный выбор темы на локальную дату, либо честное empty/withdrawn |
| GET `/me/achievements` | Четыре вычислимых условия, остальные пять not_configured |
| GET `/me/home` | statistics + active_attempt (без ключей в Exam) + последние 3 результата |

Профиль использует те же statistics/progress/achievements, без независимого
«профильного» источника истины. Публичных user_id-параметров доступа нет: SQL всегда
берёт владельца из проверенной сессии. Чужой attempt ID — 404, любой admin также owner-only.

## Семантика чисел

Сводка: completed_tests, answered_count, correct_count, wrong_count, skipped_count,
average_percent, practice_seconds, activity_streak_days, period, timezone,
data_scope=server_history, calculated_at.

- answered_count/correct_count — события ответов завершённых попыток, включая повторы,
  а не количество уникальных освоенных вопросов.
- average_percent — ROUND_HALF_UP от среднего **точных** correct/total по попыткам
  через PostgreSQL numeric. 1/6 и 1/2 дают 33%, а не 34% из округлённых 17 и 50.
- При пустом периоде completed/answered/correct/wrong/skipped = достоверные 0,
  average_percent и practice_seconds = null. Все пропуски в реально завершённой
  попытке дают честные 0%, а не отсутствие результата.
- practice_seconds — сумма уже зафиксированной серверной wall-clock длительности
  Learning/Exam, включая фон. Это не измерение активного времени экрана.
- Группы содержат completed_tests (число попыток с вопросами группы), actual counts,
  observed_questions (уникальные встреченные question IDs), average/best_percent.
  Для дисциплинарной попытки доля темы считается по её snapshot-вопросам в этой
  попытке. Нет вымышленного процента освоения всего изменяемого каталога.
- ever_wrong_question_count — уникальные вопросы с когда-либо ошибочным ответом.
  unresolved_wrong_question_count — вопросы, чей последний **данный** ответ неверен;
  более поздний правильный снимает ошибку, skip её не стирает и не создаёт новую.
- До первого завершения в теме best/ever_wrong/unresolved = null. Избранное пока не
  реализовано: favorites_count=null, favorites_status=not_configured.

## История, snapshot и безопасный разбор

История сортируется finalized_at DESC/id DESC, пагинация keyset, без общего ограничения
в 100 результатов. Limit ограничивает одну страницу; total count не вычисляется на
каждом запросе. Cursor HMAC подписан существующим content_cursor_signing_key,
привязан к владельцу, epoch, маршруту и фильтрам, сроком на час. Порча, перенос к другому
пользователю/фильтру/epoch/маршруту — 400. Курсоры истории не зависят от версии каталога.
Для следующей страницы передавайте те же фильтры. Это живая лента, не длительный SQL
snapshot: поздно материализованный timeout может потребовать обновления первой страницы.

Result-review возвращает выбранные и правильные варианты исходных revisions/options,
нейтральные пропуски, без сгенерированных ответов и без объяснений (как текущий справочный
UI). Читается только completed attempt владельца, без ограничения epoch: собственный
известный ID старого epoch остаётся историческим ресурсом. Keyset по item.position,
получение текстов/вариантов выполняется порциями и bulk-запросами, без N+1.
Во время активного Exam новый result-review закрыт общим reference lock; активные
ключи/ответы ни в историю, ни в Home не попадают. Прежний Exam `/review` сохранён.
Reference lock не является прокторингом и не отзывает ранее прочитанные материалы.

### Привязка к темам

Новая nullable колонка `attempt_items.topic_id` фиксирует тему каждого нового snapshot
для обоих режимов. Дисциплина выбирает первое каноническое вхождение вопроса в прежнем
порядке тем; дубль question_id по-прежнему исключён. FK и INSERT guard проверяют
дисциплину/принадлежность вопроса, существующий seal guard запрещает последующие правки.
Изменение topic_questions после старта не меняет прогресс начатой попытки.

В старых topic/test попытках надёжно известна attempt.topic_id — используется этот
fallback, без UPDATE неизменяемых записей. В старых discipline попытках связь не была
сохранена: общие и дисциплинарные итоги учитываются полностью, детализация темы остаётся
неизвестной. `unattributed_topic_responses` сообщает число таких итоговых response rows,
включая пропуски. Текущий каталог не используется для угадывания прошлой принадлежности.

## Календарь, время и серии

Календарная дата события вычисляется PostgreSQL как
`(finalized_at AT TIME ZONE timezone_at_start)::date`. Это неизменяемая IANA-зона,
сохранённая движком попытки. Timeout относится к дате deadline, не перезапуска worker.
Нельзя вычислять дни прибавлением 86400 секунд: календарь и границы недели/месяца
построены по локальным date, с корректным DST. Внутри графика день может содержать
23/25 часов; timestamps результатов остаются UTC.

Смена текущей timezone не переносит старые события, новая применяется к новым попыткам.
Изменение timezone во время активной попытки также не меняет её сохранённую зону.
Calendar возвращает date_policy=frozen_attempt_timezone; поле timezone обозначает
текущую зону пользователя для выбора сегодняшнего дня/недели. History отдельно
возвращает activity_date и activity_timezone каждого результата. При путешествиях
прежняя дата может временно оказаться «завтра» относительно новой зоны — это ограничение
сохранённой календарной политики, а не выдуманная активность.

Current streak — последовательность уникальных дат завершения, заканчивающаяся сегодня
или вчера в текущем календаре пользователя; иначе 0. Несколько тестов за день не удлиняют
серию. Достижение «Три дня» использует самый длинный фактический ряд в текущем epoch.
Календарь заполняет пустые даты нулём событий и null среднего, не искусственными баллами.

## Рекомендации и достижения

Heuristic selector v1: темы с данными ответами и отображаемым average_percent<70,
порядок average ASC → unresolved DESC → UUID. Рассматриваются до 100 слабейших тем из
личной истории, затем проверяется текущая публикация/доступ/непустой банк; возвращается
до 10 доступных. Это ограниченный рекомендательный список, не медицинская оценка знаний.
Нет истории/слабых доступных кандидатов — [] без фиктивных результатов.

Daily-topic в транзакции под user lock сохраняет выбор один раз в local_date: первая
доступная рекомендация, иначе детерминированный выбор по дате из стабильного списка
доступных непустых topic IDs. Сохраняются timezone/catalog_version/selector_version.
Пустой выбор фиксируется как null. Изменения истории/каталога в тот же день его не
пересчитывают; withdrawal возвращает availability=withdrawn без молчаливой подмены.
Эта маленькая таблица не является второй историей результатов. GET может лениво
зафиксировать рекомендацию, как существующий GET resume может завершить timeout.

Четыре фактических computed достижения:

- «Первый шаг»: completed_tests>=1, включая все пропуски (семантика текущего UI).
- «Три дня»: хотя бы три последовательные сохранённые календарные даты завершений.
- «Сотня»: correct_count>=100, повторы входят согласно архитектуре.
- «Без ошибок»: завершённая непустая попытка correct=total.

Это вычислимые состояния, не выдача наград: нет ledger, XP или фиктивной даты выдачи
(granted_at=null). Внутри epoch условия монотонны, поскольку результаты immutable.
Пять ненастроенных блоков/маршрутов/error-repeat имеют state=not_configured,
progress/target=null. Не создаются вымышленные составы блоков и завершения.

## Миграция и эксплуатация

0010 добавляет только nullable attribution, индекс completed history, INSERT guard и
маленькую immutable daily_recommendations. Нет backfill guessed topics, счётчиков,
нового worker, cron, аналитического сервиса, зависимостей или secrets. Существующий
EXAM finalizer продолжает работать с head 0010. Используется существующий signing key.
Schema readiness обновлена; миграции выполняются явно только в изолированной dev/test
БД по README. Нет автомиграции при старте и изменений Production/Preview.

Все read models ограничены владельцем и текущим epoch. Возвращаемые страницы <=100,
calendar <=366 дней, рекомендации <=10, Home recent=3. SQL-агрегаты работают внутри
PostgreSQL; вся история не выгружается в Python. Сохраняются действующие timeout/pool
лимиты БД. На очень большой личной истории возможен 503 по query timeout; измерения
на 1 CPU/2 GB и реальные кардинальности нужны до добавления перестраиваемого кеша.

Откат предпочтительно forward fix. Downgrade 0010→0009 блокируется при наличии новых
attribution/daily rows, чтобы не потерять смысл истории. Без новых данных допускается
возврат, 0001–0009 не менялись. Не отключать guards и не удалять данные ради отката.

Нет XP, Premium, платежей, профилирования других пользователей, progress reset API,
избранного, нового error-repeat движка или React-интеграции. UI сможет использовать
контракты без изменения дизайна отдельным этапом.
